# 사례 검토·일괄 가져오기

기존 사례와 사진을 보존하면서 신규 사례를 비공개로 등록합니다. 원본 Excel/PDF와 생성된 사례 JSON은 공개 저장소에 올리지 않습니다.

## 최초 DB 준비

1. [Supabase 대시보드](https://supabase.com/dashboard)에서 현재 사이트의 프로젝트를 선택합니다.
2. **SQL Editor → New query**에 `supabase/migrations/20261006000000_casebook_review.sql`의 내용을 붙여 넣고 **Run**을 누릅니다. 기존 프로젝트의 `public.is_admin()`과 관리자 등록을 그대로 사용합니다. 기존 관리자 초기화 SQL은 다시 실행하지 않습니다.
3. 사이트를 새로고침하고 **관리자 → 품질사례**로 이동합니다. DB 준비 안내가 사라지는지 확인합니다.

마이그레이션은 트랜잭션 안에서 실행하며 재실행 가능합니다. 기존 행에 공개·검토 필드가 없었다면 기존 공개 상태를 유지하도록 채웁니다. 이미 해당 필드가 있다면 그 값을 바꾸지 않습니다. 이후 신규 행은 `published=false`, `review_status=검토대기`가 기본값입니다. 기존 `case_no`, 문안, 사진 경로를 변경하지 않습니다.

DB 변경 전 배포하더라도 기존 공개 목록은 구형 스키마로 조회합니다. 이 호환 처리는 컬럼이 없다는 오류에만 적용하고, 기존 `published` 컬럼이 있으면 반드시 공개 조건을 유지합니다. 인증·네트워크 오류를 이유로 공개 조건을 해제하지 않습니다. DB 준비 전 신규 저장과 가져오기는 중지합니다.

## 가져오기와 검토

1. **사례 일괄 가져오기**에서 별도로 전달받은 JSON 파일을 선택합니다.
2. 신규·원본 참조 갱신·오류 건수와 각 행의 **기준·조치 내용 검토**를 확인합니다.
3. **미리보기 승인 및 일괄 저장**을 누릅니다. 오류 행은 제외되며 미리보기에 표시된 유효 행만 저장됩니다. 성공 메시지의 실제 등록·갱신 수를 확인합니다.
4. 원본 사례의 판정은 유지하고 관련 기준의 적용 조건과 문안을 검토합니다. 필요하면 사진을 첨부합니다.
5. 검토 상태를 **검토완료**로 바꾼 후 **공개**를 선택하여 저장합니다. 사진은 필수가 아닙니다.

`source_uid`가 같으면 기존 문안·사진·검토상태·공개 여부를 덮어쓰지 않고 원본 행·시트 참조만 갱신합니다. 같은 내용이라도 원본 순번이 다르면 별개 사례로 보존합니다. 가져오기는 하나의 DB 트랜잭션이며 실패하면 전체를 롤백합니다. 응답이 끊겼을 때는 새로고침해 결과를 확인하거나 같은 파일을 다시 가져올 수 있습니다.

신규 번호는 저장된 최대 `case_no` 다음부터 부여합니다. 가져오기 작업은 직렬화하며 `source_uid`에 고유 인덱스를 적용합니다. 안전성능검사 행은 이번 가져오기에서 제외합니다.

## JSON 형식

배열의 각 객체에 다음 문자열 필드가 필요합니다: `inspection_type`, `title`, `facility`, `standard_title`, `standard_body`, `cause_title`, `cause_body`, `action_body`, `prevention_body`, `finding_type`, `test_item`, `source_sheet`, `review_note`.

추가 필수 필드는 고유 문자열 `source_uid`(8~160자, 영문·숫자·콜론·하이픈·밑줄)와 정수 `source_row`(헤더 포함 원본 행, 2 이상)입니다. `finding_type`은 `보완` 또는 `부적합`입니다. `review_status=기준확인필요`를 지정할 수 있으며 그 외 상태는 검토대기로 저장됩니다. 파일에 공개·사진 경로를 넣어도 신규 가져오기는 비공개·사진 없음으로 저장합니다. 최대 2,000건/10MB입니다.

## PDF

기존 A4 표 양식에서 전체 또는 선택 사례를 출력합니다. 선택한 사례도 출력 순서에 따라 Page 1부터 새로 번호를 붙입니다. 사진은 자르지 않고 비율을 유지합니다. 인쇄 전 폰트·사진 로딩과 A4 높이를 확인하며, 넘치거나 사진 로딩에 실패하면 출력 대신 안내합니다. 브라우저 인쇄 화면에서 A4, 배율 100%, 머리글·바닥글 해제를 사용합니다. 사용자 요청에 따라 표지·목차·업무개요 복원은 이번 작업에서 보류했습니다.

## Supabase 매일 읽기

`.github/workflows/supabase-keepalive.yml`은 매일 한국시간 12:23(UTC 03:23)에 `site_config`의 식별자 한 건만 읽습니다. GitHub 예약 실행은 지연될 수 있습니다. 데이터를 쓰거나 관리자 권한을 사용하지 않습니다.

기존 **Settings → Secrets and variables → Actions → Repository secrets**의 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 재사용합니다. 이 이름의 키에는 Supabase 공개용 publishable/anon key만 넣습니다. `service_role`, `sb_secret_…`, 관리자 비밀번호는 넣지 않습니다. 응답 본문과 키는 로그에 출력하지 않습니다.

**Actions → Supabase daily read → Run workflow**로 수동 확인할 수 있습니다. 이미 일시중지된 프로젝트를 재개하는 기능은 아니며, 필요한 경우 Supabase 대시보드에서 프로젝트를 재개해야 합니다. 일정 요청만으로 서비스 가용성이나 일시중지 방지를 보장하지 않습니다.

## 권한과 안전한 설정 위치

- 프런트엔드는 기존 공개용 연결값을 사용합니다. GitHub 인증과 Supabase 관리자 권한은 별개입니다.
- 직접 사례 저장에는 사이트의 **관리자 로그인 세션**과 해당 사용자의 `public.admin_users` 등록이 필요합니다. 비밀번호는 사이트 로그인 화면에만 입력합니다.
- SQL 적용에는 Supabase 프로젝트의 **SQL Editor 실행 권한**이 필요합니다. 위 방식에는 별도 service role key 전달이 필요 없습니다.
- 로컬 개발용 공개 설정은 `.env.local`에만 저장합니다. 비밀번호·토큰·세션·원본 자료를 채팅 또는 Git에 올리지 않습니다.
- 기존 사진은 공개 Storage 버킷을 사용합니다. 사진 파일 자체는 URL을 아는 사람이 열 수 있으므로 개인정보나 비공개 원본 사진은 업로드하지 않고 공개 가능한 사진만 사용합니다.

## 검증

`npm ci`, `npm test`, `npm run build`를 실행합니다. 테스트는 PGlite PostgreSQL에서 구형 행 보존, 마이그레이션 재실행, 비공개 저장, 재등록 중복 방지, 편집 문안·사진 보존, 실패 시 전체 롤백, 공개 상태 제약, 익명·일반 로그인 사용자의 RLS 차단을 확인합니다. 테스트 데이터는 운영 DB로 전송하지 않습니다.
